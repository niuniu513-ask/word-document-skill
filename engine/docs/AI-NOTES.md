# 构建说明：AI 辅助开发与可解释性

本项目的代码由作者在 AI 编程助手辅助下完成，作者负责目标设定、方案取舍与质量判定。
这份文档记录"哪些决定是人做的、依据是什么"，便于读者（和评委）核对作者是否真正掌握该项目。

## 1. 目标是怎么定的

起点是一份 Python 写成的 Word 文档处理技能（word-document-skill），它的方法论是：
**先把 .docx 分析成 Document Specification，再在文档自身的格式体系内编辑，最后用格式校验证明没改坏。**
参赛要求"以 MoonBit 为主要实现语言"，而这份技能是 100% Python。
可选路线有三条：

1. 给 Python 技能套一个 MoonBit 壳 —— 放弃，`MoonBit 为主` 无法成立，属于"仅做简单修改"。
2. 用 MoonBit 重写整条链路 —— 采纳。
3. 只做分析器、编辑仍交给 Python —— 放弃，无法拿到"格式零漂移"这一核心卖点。

因此结论是：**用 MoonBit 从零实现一个 Word 引擎**，Python 技能退化为 agent 层（可选的调用方）。

## 2. 关键技术决定（作者拍板，AI 实现）

| 决定 | 备选 | 为什么这样选 |
| --- | --- | --- |
| 自己写 XML 解析器 | 用现成 MoonBit XML 库 | 需要保留命名空间、注释、CDATA、原始声明，并在序列化时按作用域补 `xmlns`；现成库不保证这些 |
| 元素按命名空间 URI 匹配 | 按 `w:` 前缀匹配 | Word/WPS 生产者可以用任意前缀绑定同一命名空间，按前缀匹配会漏 |
| 迭代式解析（显式栈） | 递归下降 | 一份 300 页报告的 document.xml 层级很深，递归容易爆栈 |
| 跨 run 字符级替换 | 逐 run 字符串替换 | Word 会把一个词拆进多个 run（换字体、拼写检查都会触发），逐 run 替换会漏命中 |
| 格式漂移做成可执行校验 | 人工目检 | "Formatting Delta ≈ 0" 如果是口号就没法验收，做成 diff 才能进 CI |
| 表格单元格也扫占位符 | 只扫正文段落 | 真实报告 19 处占位符全在封面表格里，python-docx 的 `paragraphs` 看不到 |

## 3. 已知取舍与不足

- 编辑器只保留"文本 + `rPr`"，会丢弃被替换 run 内的制表符/换行等非文本子节点；
  对"填占位符"场景足够，对"替换含换行的整段"不一定。
- 目录（TOC）、`numbering.xml` 定义、图片替换尚未实现，`analyze` 在这些字段上是缺省值。
- 只测了 `--target js` 与 `--target wasm-gc`；`native` 需要 MSVC，开发机上没有。
- 兼容性按 Word 2016+ / WPS 的常见写法验证，未做全量 OOXML schema 校验。

## 4. 质量是怎么判定的

1. `moon check` 零错误，`moon test` 34 个测试全绿（CI 里跑）。
2. 真实 12 部件报告：19 处占位符全部识别，填充 18 处后 `format_delta` 为 0。
3. 填充结果用 `python-docx` 交叉验证：段落数 48、表格数 9 保持不变，单元格文本正确。
4. 每个修过的 bug 都留有回归测试（命名空间前缀丢失、`parse_fragment` 返回值、声明解析偏移）。
