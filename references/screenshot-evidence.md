# 截图证据(Screenshot Evidence)

用户说"要真实的代码截图和输出截图"时,报告里那一张张图就是**证据**,不是配图。
配图可以美化,证据只能如实采集。本文件管的是后者。

适用:实验报告、课程设计、复现记录、缺陷报告、任何需要证明"这段代码真的跑过、结果真是这样"的交付。

## 1. 什么算真实截图

完整原屏必须保留编辑器身份;报告中的局部裁图通过对应原屏与映射清单追溯来源。证据应满足:

1. **能看到编辑器身份**:活动栏、文件标签页标题、行号、notebook cell 的执行序号 `[3]`。
   只剩一块黑底彩字 = 无法证明来自编辑器,也不算。
2. **与源文件一致**:图里的代码和 notebook 里保存的 `source` 逐字一致;图里的输出和 `outputs` 一致。
3. **没被重绘**:字体、主题、缩进参考线、滚动条都是用户当前环境的原样。

### 明确禁止的"伪截图"

| 做法 | 为什么不行 |
|---|---|
| 用 PIL / HTML 渲染代码文本,套一个 VS Code 皮肤 | 字体、行高、抗锯齿都对不上,行家一眼看出;本质是伪造 |
| 把代码复制到记事本/网页再截 | 没有编辑器 UI,证明不了运行过 |
| 只有输出且没有对应代码或来源映射 | 无法建立“代码 → 结果”的对应;报告允许分别裁出成对代码图和输出图,原屏需保留 |
| 把两次不同运行的输出拼在一起 | 拼接必须在同一窗口、同一文档、连续滚动内完成 |
| 拿 notebook 的 HTML 导出在浏览器里截 | 除非用户要的就是"HTML 视图",否则 UI 不对,且样式与编辑器不同 |

**合法拼接**:同一窗口、同一文档、连续滚动产生的多帧,按重叠区对齐后纵向拼合。拼接缝不得切断文字行。

## 2. 采集前固定环境

顺序很重要,漏一步就得重来。

```text
1) 在副本上真实执行   jupyter nbconvert --to notebook --execute x.ipynb --output x.executed.ipynb
2) 在编辑器里重新打开该文件,等渲染完成(webview 空白就是在渲染中)
3) 窗口最大化;不要手动拉伸(拉伸会触发重排,已抓的帧作废)
4) 关掉侧边栏/输出面板/终端,只留代码 + 输出
5) 缩放固定(如 100%),整轮采集不改变
```

**为什么先执行再打开**:采集阶段只负责"看",不负责"跑"。执行与采集分离,才能保证每一帧看到的是同一份已定型的结果;中途执行会插入新的输出块,把行号模型全部推翻。

### Windows 上的两个前置条件

- **DPI 感知**:进程不声明 DPI 感知时,`GetWindowRect` 返回的是缩放后的逻辑坐标。
  150% 缩放 + 2560×1600 物理屏,逻辑坐标只有 1707×1067,抓出来的图会被二次缩放而发虚。
  ```python
  import ctypes
  ctypes.windll.shcore.SetProcessDpiAwareness(2)   # 必须在任何窗口 API 之前
  ```
- **进程脱离作业对象**:从某些宿主(带 wsl.exe 的作业对象)里 `subprocess.Popen` 启动的 GUI 进程,
  会随父进程退出被连坐杀掉。用 `explorer.exe launch.bat` 中转启动可脱离。
  Electron/Chromium 应用还需 `--disable-gpu --no-sandbox`,否则渲染进程可能 `STATUS_BREAKPOINT` 崩溃。

## 3. 三种抓取方式,按场景选

| 方式 | 能否后台 | 能否滚轮 | 适用 |
|---|---|---|---|
| `PrintWindow(hwnd, hdc, 2)` | 能 | 不能 | 单屏内容、窗口被遮挡时取证 |
| 全屏 `ImageGrab.grab(bbox)` + 裁剪窗口矩形 | 不能(需前台) | 能 | **长文档连续滚动采集,首选**(Pillow<10 需加 `all_screens=True`) |
| `BitBlt` 桌面 DC | 不能 | 能 | 与上者等价,兼容老环境 |

实战结论:**要滚动就必须真前台**。

- `PostMessage(hwnd, WM_MOUSEWHEEL, ...)` 对 Chromium 系窗口**无效**——它只认真实输入队列里的事件。
  必须把光标移到窗口内,再用 `mouse_event(MOUSEEVENTF_WHEEL, 0, 0, delta, 0)`。
- 窗口被最小化或完全遮挡时,`PrintWindow` 在 GPU 渲染的 webview 上常返回纯黑。
  所以"后台抓 + 后台滚"这条路走不通,别在它身上耗时间。

## 4. 滚轮方向(最容易翻车的一处)

Windows 的 `mouse_event` 滚轮增量,**正数 = 向上滚(内容下移),负数 = 向下滚**。

```python
MOUSEEVENTF_WHEEL = 0x0800
def wheel(notches: int):
    ctypes.windll.user32.mouse_event(MOUSEEVENTF_WHEEL, 0, 0, 120 * notches, 0)
```

踩过的坑:把 `-120` 当成"向上",于是"滚到顶"的判断永远成立,只抓到 2 帧就以"已到底"收工。
判据——**抓完第一帧后,再滚一次若画面哈希不变,才可能是到底;方向不确定时先用 `+N` 试探并肉眼确认一帧。**

滚到顶的做法:先 `wheel(+30)`,等 300ms,再 `wheel(+30)`,连续两次画面不变即为顶部。
向下采集:每步 `wheel(-2)`,以相邻帧重叠率 0.5~0.8 为准;抓完第一段就固定步长,中途别改。

## 5. 滚动拼接

目标:把 N 帧竖直拼成一张长图,且不能有重影、不能有错位。

```text
1) 裁掉固定 UI:顶部标签栏、底部状态栏/任务栏,只保留内容滚动区
   (裁不干净 = 每一帧的 UI 都留在长图上,拼出来是几条重复的标题栏)
2) 求垂直偏移:两帧都转灰度 → FIND_EDGES → 4 倍降采样
   对候选偏移 d 逐点计算重叠区的平均绝对差,取最小
3) 在 1/2、1/1 分辨率上窄范围精修(±8px),精度落到 1px
4) 按偏移累加输出,重叠区以后一帧为准(它是更新的一次渲染)
5) 自检:对每对相邻帧算重叠区残差,>12 视为"对齐可疑",人工看一眼那段
```

**不要用行剖面。** 这是本次踩得最深的坑:notebook 页面上有大片空白带和大量结构相同的 cell,
行剖面的 L1 曲线会出现好几个几乎等低的谷,匹配稳稳地锁在错误位置。
实测同一对帧:

| 方法 | 估计偏移 | 重叠区残差 | 结果 |
|---|---|---|---|
| 灰度行剖面 | 635px | 35.8 | 拼出来内容被复制一遍 |
| 灰度二维块匹配 | 148px | 5.4 | 基本对齐 |
| **边缘二维块匹配** | 150px | 5.4 | 对齐且稳定,总高与理论值一致 |

纯灰度二维匹配在 Matplotlib 的渐变色块上仍会漂(渐变区平移后依然相似)。
`FIND_EDGES` 把平滑渐变压成近黑,只留文字笔画和坐标轴框,匹配才真正锚定在结构上。

**拼接失败的症状**:文字上下重影(偏移偏小)、内容被跳过(偏移偏大)、
同一段代码出现两次(某帧偏移被判小,重叠区没被覆盖)、接缝横切一行字(偏移对但裁切线落在字形上)。
最后一种要靠裁切阶段规避(见下节),不要靠调偏移硬凑。

**重叠率**:低于 0.35 时匹配信息不够,`capture_notebook.py` 会警告并建议减小 `--step`;
0.5~0.8 最好。重叠 0.9 也不会出错,只是帧数变多、抓得慢。

## 6. 按单元格裁切:别从长图上切

长图能证明"连续",但**不能用来切单元格**——切点极易落在两帧接缝处,把一行代码拦腰切断。

正确做法:在长图上**定位**单元格的上下边界,再回到**包含该区间的单帧原图**上裁像素。

定位靠 notebook 结构,不靠图像识别:

```python
nb = json.load(open("test-1.ipynb", encoding="utf-8"))
units = [len(c["source"]) for c in nb["cells"]]     # 每个 cell 的源码行数
# 实测行高模型:cell 高度(px) ≈ 56 + 28 * 行数   ← 与字号/缩放绑定,换环境必须重标定
exp = [56 + 28 * n for n in units]
```

先算每个 cell 的期望高度,与长图总高对账;误差超过 3% 说明行高模型不适用(换过缩放/字体),
回到单帧上量两三个 cell 的像素高重新拟合。

裁切时的两条硬约束:

- **上边界取 cell 容器上沿**(卡片顶部圆角处),不是第一行文字的 y;留 8~14px 内边距。
- **下边界取输出区最后一行像素 + 12px**,不要用"下一个 cell 的顶"直接当边界(会带进下个 cell 的头部)。

裁完必做的一步:生成裁边版(`*_t.png`),按内容外接框再收紧一次。
输出区常常只有左侧 200px 有内容、右侧一大片纯背景,不裁就是一根"宽黑条",插进 Word 后字小到看不清。

```python
def tight_bbox(a, bg=(18, 19, 20), tol=14, min_density=5):
    """返回内容外接框;密度阈值过滤掉卡片圆角与滚动条这类零星像素。"""
    d = np.abs(a[:, :, None, :].astype(int) - np.array(bg)).sum(axis=3).min(axis=2)
    mask = d > tol
    cols = np.where(mask.sum(axis=0) > min_density)[0]
    rows = np.where(mask.sum(axis=1) > min_density)[0]
    if not len(cols) or not len(rows):
        return None
    return cols.min(), rows.min(), cols.max() + 1, rows.max() + 1
```

阈值 `min_density` 别设太小(1~2),否则边框圆角的那几个像素会把外接框撑到整张图。

### 6.1 缩放变化后的坐标与证据映射

每次捕获绑定同一帧的窗口、文件/cell、代码或输出类型、原屏尺寸、坐标空间、裁剪框、比例与原点。CSS 坐标、系统逻辑坐标、原屏物理像素不能混用。不要只用缓存的 `devicePixelRatio` 或“原屏宽/viewport宽”：整屏截图可能含窗口外像素，编辑器与系统缩放也可能不同。

缩放、换行、窗口尺寸或滚动位置变化后，旧矩形失效。重新测量并先预览一组代码/输出图，确认首末行完整，输出没有变成下一题代码。输出图只有数字时，通过保留原屏的邻接关系及执行副本核对来源。

可用工具按明确的物理像素框裁图（不自动推断语义或缩放）：

```bash
python scripts/crop_evidence.py raw.png cell5-code-v2.png --box 65 640 1200 180 --identity "test-1/cell5/code"
# 只有测量已证明坐标比例时才传 --scale；--origin 为截图中的物理像素偏移
python scripts/crop_evidence.py raw.png cell5-output-v2.png --box 80 650 900 110 --scale 1.25 --origin 0 0 --identity "test-1/cell5/output"
```

工具保留原屏、拒绝越界和覆盖、生成坐标与 SHA-256 旁车 JSON；越界检查能发现部分失效坐标，**在图内但裁错 cell 的矩形仍需人工核对**。示例数字仅用于解释参数，不可套用于其他窗口。

为每题建立 notebook/cell → 原屏 → 代码裁图/输出裁图 → DOCX 图片引用 → 分析的清单。替换裁图或重新采集后，从更新后的清单重建最终文档并重新渲染。DOCX 内嵌图片不会随磁盘 PNG 自动刷新；必要时对比内嵌图与裁图的像素哈希（若重新编码，比较解码后像素）。`verify_evidence.py` 只检查结构与图像特征，不能证明题号、代码或输出正确。

## 7. 清掉编辑器/系统的临时 UI

这些不是证据,是垃圾,留在图里既难看又会被问"这是什么":

| 目标 | 特征 | 处理 |
|---|---|---|
| VS Code 右上角临时提示 | 遮挡内容或占用版面 | 关闭提示后重截,或裁掉内容区外的提示 |
| Windows 任务栏 | 底部约 60~90px 的深色/彩色条 | 裁掉窗口矩形之外的区域即可(按窗口 rect 裁) |
| 右侧空白 / 缩略图 | 内容列右侧连续无内容的区域 | 按列密度裁到最后一个有内容的列 + 24px |
| 通知气泡 / 输入法候选框 | 突变的高对比色块出现在固定位置 | 重新抓一帧,别去 P |

证据图只做裁剪及保真缩放;不要涂抹 UI 像素,语法高亮与提示色可能相同。遮挡代码或输出时重新采集。

## 8. 图片进 Word 的比例(决定"能不能看清")

**核心原则:所有截图在 Word 里呈现的字符大小应当一致。**
不是"每张图都撑满版心",也不是"统一 10cm"——那会让短图字巨大、长图字如蚁。

经验换算(基于 100% 缩放、正文小四/12pt、版心 15.2cm):

```
width_cm ≈ width_px × 0.0245
```

即 620px 的代码图 → 15.2cm 恰好铺满版心;195px 的小输出图 → 4.8cm,字符视觉大小与前者相同。

实现要点:

- 只给 `width_cm`,让高度自适应——优先只设宽度;若必须同时设宽高,两者应按同一比例计算并核对 XML 中的实际尺寸。
- 加下限防止碎图被放成邮票:`max(4.0, min(15.2, w * 0.0245))`。
- 上限用版心宽度,别用页面宽度;超版心的图会被 Word 压回来,还会挤断行。
- 图注在图下方、居中、五号;图与图之间不要用空行,用段前段后间距。

比例系数会随正文号数变化:`width_cm ≈ px × 0.0245` 对应 12pt 正文。正文改小四(12pt)以外时按比例缩放,
并**在成品里量一次实际字符高度**核对,别假设。

## 9. 证据完整性核对(交付前的硬闸门)

目检会漏,数字不会。交付前用文档本身的文本层与图片对象对账:

```bash
python scripts/verify_evidence.py 报告.docx --label 代码截图 --label 实验结果截图 -o evidence.json
```

判定标准:

1. **标签数 = 应有题数**。"代码截图:" 出现次数应等于有代码的题数;"实验结果截图:" 应等于有输出的题数。
2. **图片数 = 标签数**。少一张 = 漏插;多一张 = 插了图却没有标签(读者不知道它是什么)。
3. **无输出不得留空图**。某个 cell 本来就没输出(如纯 `import`、纯赋值),要**删掉该题的输出标签**,
   而不是插一张全黑或全白图。
4. **每张图的紧凑度**。内容宽度 / 图片宽度 < 0.35 视为"宽黑条",必须重新紧裁。
5. **无超高图**。高宽比 > 8 的长图在 A4 上没法读,应拆成多张,或改用纵向长图 + 页内缩放。

数量应由当前任务的题号映射和有输出的代码单元格计算,不要沿用历史报告常量。

## 10. 文字结论必须与截图对得上

截图摆在那里,分析却写错数字,是这类报告最致命的失分点,而且自己看不出来。

交付前逐条核对实测数字,必须能追溯到对应截图或执行输出。理论值、公式推导值和建议值须标明性质,不要求它们原样出现在截图中:

| 本次真实事故 | 症状 | 规避 |
|---|---|---|
| 把 `np.prod` 写成"累积乘积" | 输出是 `[66 120]`,cumprod 应是 `[11 66 120]` | 写之前回看输出数组长度 |
| 分析里出现 0.9981 | 实际输出是 0.7364,数字是上一版残留 | 数字全部从输出复制,不凭记忆 |
| 写"dog 出现 5 次最多" | 输出显示 cat、dog 各 4 次并列 | 频次统计要数输出行,不数印象 |

规则一句话:**实测结论能追溯到本次输出,推导与理论值明确说明依据。**

## 11. 反例清单(照抄会翻车)

- ❌ 用 `PostMessage` 发滚轮 → Chromium 收不到,抓 20 帧全是同一屏。
- ❌ 滚轮方向记反 → "已到顶"恒成立,只抓 2 帧就收工。
- ❌ 采集途中执行 cell → 输出块增减,行高模型全错,后续裁切全废。
- ❌ 从拼接长图直接切单元格 → 接缝切断文字,交上去就是一行半截字。
- ❌ 所有图统一 15.2cm → 短图字大如标题,长图字小如注释。
- ❌ 同时设置宽和高 → 图被拉扁,表格文字变形。
- ❌ 没输出的 cell 也插一张图 → 读者看到纯黑方块,以为程序崩了。
- ❌ 只渲染 PDF 不看图就交付 → 图片全黑、图注错位、标题孤立全看不见。
- ❌ 截图里留着浏览器标签、聊天窗口、通知 → 隐私泄露,必须重抓(并且删掉含隐私的中间帧)。
